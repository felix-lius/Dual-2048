## 0. 文档约定

### 0.1 设计支柱（Design Pillars）
为防止「支柱漂移」，全文设计决策统一对齐以下三条支柱：
1. **双线协同挑战**——核心动词是「一次滑动，双盘同步」，玩法张力来自双盘的并行推进与资源权衡。
2. **低门槛、高上限**——滑动即玩、一局短平快；硬核模式与辅助资源管理提供深度。
3. **公平可控的辅助**——撤销 / 冻结是「缓压工具」而非「碾压手段」，因此限次、防刷、不可无限滚雪球。

## 1. 游戏概述

### 1.1 游戏概念（Concept）
《双倍 2048：双重挑战》是在**单一窗口内并排两个独立 4×4 棋盘**的 2048 变体。玩家用一次方向键 / 触屏滑动**同时驱动两个棋盘做相同的滑动与合并**；两个棋盘各自独立生成新块、独立计分。游戏考验玩家在「双线并行」下的规划与辅助资源（撤销 / 冻结）管理。

一句话定位：**一次滑动，双盘同步；在双重压力中冲上 2048。**

> v1.1 补充：**游戏无首页 / 主菜单**（单页架构，见 §0.2 C1）。加载即进入双盘对局，模式（硬核 / 休闲）与语言（中 / EN）在游戏内 HUD 的 SegToggle 上即时切换。

### 1.2 核心特色（Features）
- **双盘同步**：一次输入，双盘并行结算、同步播动画。
- **双模式**：硬核「任一盘死局即负」/ 休闲「达标退役 + 4 场景规则」（见 §2.3、§6.3）。模式在游戏内 HUD 分段切换。
- **两支辅助**：撤销（Undo，回退一步）、冻结（Freeze，锁定一盘争取发育空间）。
- **单页 + SegToggle**：无首页；语言 / 难度以两段胶囊切换，难度开局前自由切、开局后锁定需确认（见 §2.3、§5.1）。
- **卡通圆润视觉**：暖奶油→蜜桃渐变背景、糖果色块（见 §4.2，美术圣经已落地）。
- **中英双语**：英文为主、中文为辅，in-place 切换（见 §7 i18n）。
- **跨端 H5**：横屏并排、竖屏上下堆叠，适配桌面与移动端内嵌视图。

### 1.3 目标用户
- 休闲益智玩家、2048 老玩家、移动端碎片化时间用户。
- 年龄段约 10–45 岁；强调「上手零门槛、精通有深度」。

### 1.4 平台与发布
- 首发平台：**平台**（网页 + APP 内嵌 iframe）。
- 形态：HTML5，纯前端、无外网依赖（见 §10.1、§10.5）。
- 屏幕：横屏优先；竖屏自动上下堆叠（见 §4.1、§10.4）。
- 全屏：保留 F 键全屏触发（键盘环境）；移动端全屏由 平台APP iframe 原生提供，**游戏内无全屏按钮**（见 §0.2 C2/C7）。

### 1.5 技术引擎
- **Phaser 3（3.80.1）**，本地化到 `vendor/phaser.min.js`，**无任何外网 / CDN 依赖**（见 §10.1）。
- 交互层不使用 Phaser 自带交互命中（零 `setInteractive` / `disableInteractive` / `input.hitArea` / `topOnly`），改用自研 `InteractionManager` 几何矩形命中（见 §10.6）。

## 2. 核心玩法

### 2.1 基础规则
- 每个棋盘为 4×4 网格，初始各自生成 2 个新块。
- 玩家输入一个方向（上 / 下 / 左 / 右），该方向**同时**作用于两个棋盘：
  - 棋盘内所有方块沿该方向滑动，相邻相同数字合并为双倍值。
  - 合并规则与经典 2048 一致（一次滑动中，一个块最多合并一次）。
- 滑动后，发生移动的棋盘独立生成一个新块（见 §2.2、§6.1）。
- 每个棋盘独立计分；**总分 = 左盘得分 + 右盘得分**。

### 2.2 双盘同步机制（关键）
- **同帧并行结算**：输入事件触发后，两个棋盘在**同一帧内并行计算**滑动 / 合并结果。
- **同步动画**：双盘动画**起点一致、时长一致**，同时播放（不得一盘先动一盘后动）。
- **新块 / 计分对齐**：**只有在本回合发生「有效移动」的棋盘，才生成新块并计分**；未发生移动的棋盘（例如因被冻结而锁定、已退役、或该方向上本就无变化）不生成新块、不计分。
- 该规则保证死局判定、胜负判定与「有效移动」口径完全对齐（见 §2.3、§6.3）。

### 2.3 胜负判定
- **胜利目标（胜利块）**：任一棋盘**合出 2048 方块（该盘 maxTile() ≥ 2048）**即触发胜利状态（玩家可选择继续「无尽模式」或结束）。
  - 注意：**「胜利」以「合成出 2048 方块」为准**，与「休闲退役阈值（棋盘累计自身总分 ≥2048）」是**两套独立语义**（见 §6.3 注释）。
- **失败（硬核模式，默认）**：**任一非冻结 / 非退役棋盘进入死局**（四个方向均无法移动 / 合并）即判负。
- **失败（休闲模式）**：按「4 场景规则」判定（见 §6.3）：
  - (a) 一盘死局且**自身总分 <2048** → 该盘负（整局负）。
  - (b) 一盘死局且**自身总分 ≥2048** → 该盘**退役**（显示 DONE），另一盘继续。
  - (c) 退役后，剩余盘死局且其**自身总分 <2048** → 整局负。
  - (d) 退役后，剩余盘**合出 2048 方块** → 整局胜（双达标 `bothDone`）。
  - 若剩余盘死局且自身总分 ≥2048 → 该盘也退役 → 双达标胜利（bothDone）。
- **胜负优先级：先胜后负**。每回合先判定是否有棋盘合出 2048（胜），再判定死局（负）；若同一回合同时出现「达标」与「死局」，以**胜利**为准（见 §6.3）。
- **冻结 / 退役与胜负无关**：胜负判定只看是否达标 / 死局，与某盘是否处于冻结或退役状态无关（冻结盘不参与死局判定，退役盘已退出）。
- **模式切换（难度锁定，ITER-V10）**：
  - 难度（硬核 / 休闲）在 HUD 以 SegToggle 切换（见 §4.1、§5.1）。
  - **开局前（`hasMoved=false`）**：可自由切换，立即生效于当前局。
  - **首次有效移动后（`hasMoved=true`）**：直接切会弹出模态确认「切换难度并重开一局？」（确认 → 切难度 + 重开当前局；取消 → 保留）。语言切换**始终可切**（不受 `hasMoved` 限制）。
  - 设计理由：避免对局中途改难度造成状态歧义，同时保留开局前的自由体验。

### 2.4 「有效操作 / 有效移动」统一定义（全文档唯一口径）
> **玩家按一次方向键（或一次有效滑动手势）后，若至少一个棋盘发生了「移动」或「合并」（即棋盘状态改变），则该次输入记为一次「有效操作 / 有效移动」（valid global move）。**

- 若两个棋盘在该方向上都无任何变化，则**不是**有效移动（不计入冻结计时、不生成新块、不消耗资源、不计步、不触发得分奖励）。
- 此定义统一适用于：冻结计步（§3.2）、撤销判定（§3.1）、新块 / 计分对齐（§2.2）、死局判定（§2.3）、难度锁定触发（§2.3）。
- 无效滑动**不消耗**冻结计时（明确区别于「每次按键减 1」的旧表述）。

### 2.5 得分规则
- 每次合并产生分数，分值为**合并后新块的面值**（例如两个 2 合并成 4，得 4 分；两个 1024 合并成 2048，得 2048 分）。
- 双盘独立累计，HUD 分别展示左 / 右盘分与总分（竖屏为「上盘 / 下盘」caption，见 §4.1）。
- 总分用于：最高分记录（§3.3）、冻结得分奖励阈值（§3.2）。
- **退役阈值**使用「棋盘自身累计总分」（非单块面值、非两盘合计），见 §6.3。

## 3. 系统详细设计

### 3.1 撤销系统（Undo）
- **免费额度**：每局 **5 次**免费撤销（`UndoManager(40, 5)`：环形缓冲容量 40，免费 5 次）。
- **撤销行为**：恢复「最近一次有效全局移动」前的双盘棋子布局与计分快照（回退一步）。退役状态（`retired`）也纳入快照，可回退到退役前。
- **环形缓冲**：历史快照定长 40（`capacity`），超出丢弃最旧，防内存增长。
- **耗尽后的激励视频续次【桩 / TBD】**：
  - 设计意图（v1.0）：免费 5 次用尽后点击撤销 → 弹激励视频 → 看完得 5 次临时撤销（仅当局、不跨局累积、当局内无获取上限）。
  - **代码现实（v1.1）**：当前 `onUndoClick` 在 `undoLeft<=0` 时仅弹出警示 Toast 并调用 `平台.requestAd('rewarded')` **占位桩（仅 `console.log`）**，**尚不真正发放临时撤销次数**。`UndoManager` 也无「临时次数」概念。真实发放待 平台 SDK 接回后实现（见 §9.1、§16.2）。
- **防刷约束**：
  - 撤销**不影响**撤销次数本身、冻结次数、冻结锁定状态与计时（元资源不随撤销回滚）。
  - 冻结得分奖励（`lastMilestone` 单调里程碑）**不随撤销回滚**（明确防刷，见 §3.2、§16.1）。
- **边界**：对局未开始 / 已结束不可撤销；已无历史快照时撤销按钮置灰（`canUndo()` 守护）。

### 3.2 冻结系统（Freeze）
- **激活次数**：每局 **3 次**冻结激活（`FreezeManager(3, 1000)`：免费 3 次）。
- **激活行为**：点击冻结 → 进入「选择要冻结的棋盘」状态（提示「点击要冻结的棋盘 左 / 右」）→ 点击目标盘锁定该盘。被锁定盘在冻结期间：
  - 不响应滑动（不移动 / 不合并）；
  - 不生成新块、不计分（与 §2.2 对齐）；
  - 覆盖深海军蓝半透明遮罩 + 锁形图标 + **剩余步数（5 步指示）**。
- **冻结计时（时长计量）**：
  - **时长 = 5 次有效全局移动**（v1.1 最终定稿，由草稿 / v1.0 待拍板的「3 或 5」定为 **5**；实现于 `FreezeManager.applyTo` 中 `steps[i] = 5`）。
  - 以「有效全局移动」为单位倒计时：每发生一次**有效全局移动**（见 §2.4），当前冻结计时 **-1**（无效滑动不消耗）。
  - 计时归 **0** 时**自动解除**锁定。
- **得分奖励（额外激活次数）**：
  - 双盘**总得分**每增加 **1000 分**，冻结激活次数 **+1**（`bonusLeft += gained`，仅当局有效、无上限）。
  - 触发时 UI 给出 Toast 提示（如「得分奖励：冻结 +1」）。
  - **防刷**：奖励依据 `lastMilestone` 单调里程碑计算，**不随撤销回滚**（快照序列化刻意不含 `lastMilestone`）。
- **约束**：
  - **冻结中不可再次冻结**（须等当前冻结解除，或本局冻结已用尽 / 两盘均已冻结则按钮置灰）。
  - 得分奖励不随撤销回滚（防刷）。

### 3.3 分数与记录
- **当前分**：本局双盘总分，HUD 实时展示。
- **最高分（Best）**：
  - 以**居中醒目的胶囊徽章**展示于 HUD 顶部正中（墨蓝灰半透明胶囊 + 白字，破纪录时短暂变为薄荷绿高亮约 900ms）。
  - 首版为**本地最高分**（`localStorage` 持久化，键 `dual2048.bestScore`，见 §10.3）。
  - **跨平台排行榜需后端，列为后续阶段**（见 §14），首版不实现。
- **记录范围**：仅持久化「最高分」与「语言设置」（键 `dual2048.lang`）；**当前对局状态不持久化**（刷新即新局）。

## 5. 辅助交互流程

### 5.1 输入 → 结算主循环（含难度锁定）
```
玩家输入方向（键/滑动）
   │
   ├─ 冻结选择期？→ 提示「选择冻结目标」，不消费滑动（不静默吞）
   ├─ 动画锁(busy)内？→ 单向缓冲 pendingDir（动画结束续跑，不丢输入）
   │
   ├─ 并行计算左盘、右盘滑动/合并结果（同帧，跳过冻结/退役盘）
   │
   ├─ 判定「有效全局移动」（至少一盘状态改变？）
   │      ├─ 否 → 忽略（不计时、不生成、不计分、不切难度锁）
   │      └─ 是 → 压栈快照 + 置 hasMoved=true（难度自此锁定）
   │             ├─ 播放同步动画（仅对发生移动的盘 render，消除冻结盘闪烁）
   │             ├─ 发生移动的盘：生成新块 + 计分
   │             ├─ 冻结计时 -1（若处于冻结）
   │             ├─ 触发得分奖励判定（每+1000分 +1冻结）
   │             └─ 胜负判定（先胜后负）→ 达标/死局/退役处理
   │
   └─ 难度切换（SegToggle）：
         ├─ 开局前(hasMoved=false) → 直切，立即生效
         └─ 开局后(hasMoved=true) → 弹确认弹窗「切换难度并重开一局？」
                ├─ 确认 → 切难度 + restart
                └─ 取消 → 保留
   语言切换：始终可切（in-place，不重启场景）
```

### 5.2 撤销流程
```
点击撤销
   ├─ canUndo()（免费>0 且 有快照）→ 消耗 1 次，回退一步（含 retired 状态）
   └─ 不可撤销（undoLeft=0 或 无快照）
          ├─ undoLeft>0 但无快照 → Toast「暂无可撤销」
          └─ undoLeft=0 → Toast 警示「撤销已用完」+ 调 平台.requestAd 占位桩
                （【桩】真实「看广告发 5 次临时撤销」待 平台 SDK 接回，当前不发放）
```

### 5.3 冻结流程
```
点击冻结（且当前未冻结、且本局仍有激活次数）
   ├─ 进入「选择冻结目标」状态（Toast「点击要冻结的棋盘 左/右」）
   ├─ 点击目标盘
   │     ├─ 该盘未冻结 → 锁定该盘，steps=5，启动计时
   │     └─ 该盘已冻结 → Toast「该盘已被冻结」，取消选择
   ├─ 再次点击冻结 → 取消选择
   └─ 每次有效全局移动 计时 -1；计时=0 → 自动解除
得分每 +1000 → 冻结激活次数 +1（Toast 提示）
```
> 冻结选择期输入不静默吞：方向输入给 Toast 提示，点按用于选盘（见 §10.6 `consumed` 隔离）。

## 6. 难度与平衡

### 6.1 新块生成概率
- 每个棋盘**独立**生成新块，各自判定：
  - **约 90% 概率出 2**，**约 10% 概率出 4**（数值为默认值，可作平衡微调参数）。
- 仅在「发生有效移动的盘」上生成（见 §2.2）。
- 单回合最多每盘各生成 1 个新块。

### 6.2 难度曲线
- 随盘面被填满，可合并空间下降，死局概率上升（与经典 2048 一致）。
- **双盘叠加效应**：硬核模式下任一盘死局即负，使实际难度高于单盘 2048；休闲模式显著降低挫败感（退役机制兜底）。
- 辅助资源（撤销 / 冻结）提供「缓压」而非「通关」——限次 + 防刷保证不出现主导策略（design pillar 3）。

### 6.3 边界情况规则
| 场景 | 判定 |
| --- | --- |
| 同回合双盘**同死局** | 硬核：负；休闲：两盘均 <2048 → 负；两盘均 ≥2048 → 双退役 → 双达标胜 |
| 同回合双盘**同达 2048（合成块）** | **胜利**（先胜后负） |
| 同回合一盘合成 2048、一盘死局 | **胜利优先**（先胜后负） |
| 冻结中的盘先合成 2048 | **算赢**（胜负与是否冻结无关） |
| 仅一盘死局（另一盘存活且可动） | 硬核：负；休闲：该盘总分<2048→负；该盘总分≥2048→退役、另一盘继续 |
| 退役盘之外那盘也死局 | 休闲：剩余盘总分<2048 → **负**；剩余盘总分≥2048 → 也退役 → **双达标胜** |
| 退役后剩余盘合成 2048 | 休闲：**胜（bothDone）** |
| 被冻结盘「死局」 | 冻结盘视为暂停、**不参与死局判定**；以非冻结盘状态为准 |
| 有效移动但某盘无变化 | 该盘不生成新块 / 不计分（§2.2） |
| 输入无效（双盘均无变化） | 不计为有效移动，不计时、不生成、不消耗资源、不置 hasMoved |

**关键语义区分（务必注意）**：
- **胜利块条件** = 某盘 `maxTile() ≥ 2048`（即**合成出 2048 方块**）。
- **休闲退役阈值** = 某盘**自身累计总分 `score ≥ 2048`**（RETIRE_SCORE=2048，与「合成 2048 方块」是两回事：一个棋盘可能在总分早已破 2048 后仍没合成出 2048 方块，反之亦然）。
- 两者不要混淆：退役看「分」，胜利看「块」。

## 9. 广告变现

### 9.1 激励视频（与撤销绑定）
- **触发**：免费撤销用尽后点击撤销（见 §3.1）。

## 10. 技术规范

### 10.1 Phaser 3 本地化
- 使用 `vendor/phaser.min.js`（3.80.1），**无 CDN / 外网请求**。
- 所有资源（JS / 美术 / 字体）随包发布，符合 内嵌 iframe 离线运行要求。

### 10.2 性能预算
- 双盘同帧并行结算 + 同步动画，目标 **≥ 30 fps**（低端机可降级动画复杂度 / 简化过渡）。
- 建议：合并计算与渲染分离；避免每帧全量重绘；对象池复用块精灵；仅对发生有效移动的盘 render（消除冻结盘闪烁、降开销）。

### 10.3 持久化
- `localStorage` 持久化：最高分（键 `dual2048.bestScore`）、语言（键 `dual2048.lang`）。
- **不对局状态持久化**（刷新即新局）。

### 10.4 适配
- 横屏并排 / 竖屏堆叠的响应式布局（见 §4.1，纯函数 `computePortraitHudRects` 保证不重叠）。
- 触屏滑动手势 + 键盘方向键双输入（`src/input.js`）。
- **输入判定依赖 `InteractionManager` 的 `consumed` 标志**（见 §10.6），不再依赖 Phaser 自带交互命中。

### 10.5 无外网依赖
- 全包自包含，符合发布与离线运行要求（见 §13）。

### 10.6 交互架构（InteractionManager，ITER-V9 关键）
> 本节为 v1.1 新增，记录交互层彻底重写的设计与约束。

**为什么这样设计（根因）**：
- 原型长期存在「按键 / 按钮点击失灵 / 仅左半响应 / 连点崩溃」等顽固 bug。根因在于 Phaser 自带交互体系（`setInteractive` / `disableInteractive` / `input.hitArea` / `topOnly`）与容器原点、深度、resize 后尺寸不同步，且按钮销毁后纹理命中区悬空；增量补丁（去动作锁、修命中区偏移、竖屏自适应、审计 setInteractive）始终未能根治（换浏览器 + 手机 + 关插件仍失灵，确认为 100% 代码 bug）。
- ITER-V9 决定**彻底重写交互层**，删除全部 Phaser 交互 API。

**架构**：
- `src/interaction.js` 的 `InteractionManager`：在场景 `input` 上注册**唯一一个**全局 `pointerdown`。
- 维护一个**有序矩形句柄数组**（`items`，尾部 = 顶层 z）；按钮 / SegToggle / 隐私链接 / 模态遮罩均通过 `register(rect, onClick)` 注册一个**几何矩形命中区**。
- 命中规则：pointerdown 时从**顶层→底层**（末→首）遍历，找到第一个 `enabled && visible && pointInRect` 的项 → 调 `onClick()` → 置 `consumed=true` 并停止向下穿透。
- `input.js` 在自身 pointerdown 处理器中读取 `interactions.isConsumed()`：**已被按钮消费的手势不再当滑动 / 点击**（从根隔离按钮点按与棋盘滑动手势）。
- 绘制与命中**共用同一份 rect**（位置 / 尺寸即命中矩形），杜绝「画得到但点不到」。

**对未来 UI 工作的约束（务必遵守）**：
1. **禁止**使用 Phaser 的 `setInteractive` / `disableInteractive` / `input.hitArea` / `topOnly`。所有可点元素必须经由 `InteractionManager.register` 注册几何矩形。
2. **命中矩形必须与绘制矩形同源**（同一 rect）；改尺寸 / 位置须同步 `setRect` / `setSize`（如 `Button.setSize` / `SegToggle.resize`），保证视觉与命中一致。
3. **SegToggle 拆为左右独立半矩形**（左半 `option[0]`、右半 `option[1]`），各自 register；点击当前项无操作。彻底消除「仅左半可点」。
4. **按钮零动态效果**：`drawButton` 仅两态（normal / disabled），无 scale / 变色 / 定时 / tween。新增任何按钮视觉反馈都不得引入动态效果（维持「按下即响应」）。
5. **模态弹窗**用 InteractionManager 实现：先注册全屏 dim 矩形（底层，消费手势、阻断穿透到棋盘 / HUD），再注册 Confirm / Cancel 按钮（后注册 = 顶层，优先命中）；关闭时 `destroy` 全部句柄（见 `game.js._askSwitchMode` / `_closeModeSwitchDialog`）。
6. **禁用项不消费手势**：`enabled=false` 的句柄在遍历中被跳过，其手势会「落空」到场景 tap（不会误触其它按钮）——这是预期行为。
7. **隐私链接等非常规可点元素**用几何矩形（由文本测量尺寸推算），**绝不**用纹理 / Alpha 命中（旧根因：Text 销毁后 `frame.data` 悬空导致崩溃）。
8. **注册顺序即 z 序**：overlay / 模态须最后注册（置顶）；顺序错误会导致点击路由错乱。
