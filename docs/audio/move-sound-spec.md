## 0. 本次最重要的发现（请先读这一节）

**音频圣经从一开始就写对了，是代码实现跑偏了。**

`design/audio/audio-bible.md` 第 72 行与第 139 行对 `swipe` 的原始规定是：

> | 3 | `swipe` | … | **微妙 whoosh（风声）**，方向无关、很轻 | must | 白噪声 → 带通滤波（**~800Hz–1.5kHz**），120–200ms，**向下扫频**，低增益；不抢戏 |
>
> | whoosh（swipe） | `BufferSource(白噪声)` → `BiquadFilter(**bandpass 800–1.5k, Q~1**)` → `Gain`(env，**下扫**) | 120–200ms |

而项目最初落地的代码是：

```js
this._noise({ dur: 0.09, peak: 0.05, band: 2200, q: 0.7, sweepTo: 4200 });
```

**逐项比对，三条全违反：**

| 圣经规定 | 原始代码 | 偏离 |
| --- | --- | --- |
| 带通 800 Hz – 1.5 kHz | 2200 → 4200 Hz | **整体高了约 1.5 个八度**，正落在人耳最敏感的 3–4 kHz 刺耳区 |
| **向下**扫频 | **向上**扫频 | **方向反了** |
| Q ~ 1 | Q = 0.7 | 偏宽（Q0.7 = 1.92 个八度带宽，见 §2.4） |

> **结论：用户从头到尾都没听到过圣经里那只 whoosh。** 他当年否决的「不够好听」，否决的是一只**跑高了 1.5 个八度、扫反了方向**的错误实现。
> 之后的方案 A（玻璃叮）与方案 C（木质嗒）都是在「whoosh 路线已被证伪」这个**错误前提**上另起炉灶 —— 两次绕路的根因在此。
>
> **因此 v3.0 不是「第三次换音色」，而是第一次把 audio-bible §2 #3 真正实现出来。** 这也是我对主理人诊断的最重要一条补充（完整验证/修正见 §1.3）。

## 1. 任务背景与三次方案迭代对照

### 1.1 现状

`src/audio.js` 中 `play('swipe')` 当前实现（**235–248 行**）是 **v2.0 木质嗒**（`_tone` triangle 300Hz + `_noise` bandpass 1800→1400Hz 两层）。

### 1.2 三次方案迭代对照（★ 后续维护必读）

| # | 方案 | 实现 | 用户评价 | 被否的**声学成因**（诊断） | v3.0 的应对 |
| --- | --- | --- | --- | --- | --- |
| 0 | **原版 whoosh** | 单层 `_noise({dur:.09, peak:.05, band:2200, q:.7, sweepTo:4200})` | 「不够好听」 | ① 频段高了 1.5 个八度，能量压在 3–4 kHz 耳道共振区 → 刺；② **上扫**与衰减包络物理矛盾（越轻越高）→ 不自然、发毛；③ 可听扫程只有 **0.46 个八度**（见 §2.3），运动感反而不足 → 听成「呲」不是「嗖」 | **保留 whoosh 路线**，把频段整体下移约 1 个八度、扫向翻转为下扫、可听扫程加倍到 0.94 个八度 |
| A | **玻璃叮** | 三层 sine（1000 / 2000 / 2760 Hz） | 「太亮太飘」 | 纯 sine 高频、无低频支撑 → 通透但没重量；且**完全没有频率移动 → 零运动感** | 放弃打击音路线。运动感只能靠**扫频**产生，静态音高做不出「嗖」 |
| C | **木质嗒** | `_tone` triangle 300Hz + `_noise` 1800→1400Hz | 「不算好听」 | 方向性错误：用户要的是**运动物体掠过**，木质嗒是**静止物体被敲击**。两者是相反的语义 —— 再怎么调音色都对不上 | 彻底放弃「打击/落点」隐喻，回到「气流掠过」隐喻 |
| **D** | **轻柔气流 whoosh**（本规格） | **单层** `_noise({dur:.11, peak:.038, band:1800, q:1.3, sweepTo:450})` | 待验收 | — | 见下文 |

**从这张表能提炼出三条不可再犯的教训：**

1. **「嗖」= 扫频。** 方案 A 被否的根因是零频率移动。任何没有 `sweepTo` 的方案都做不出运动感，**下次不要再提打击音路线**。
2. **「不好听」≠「路线错」。** 原版 whoosh 的问题是调音（频段/扫向），不是路线。当年若直接调参而不是换路线，可以省掉 A、C 两轮。
3. **隐喻要对。** 移动方块 = 物体位移 = 气流掠过；不是敲击、不是叮当。**语义对不上时，音色调得再精细也会被否。**

### 1.3 对主理人诊断的验证与修正

主理人的诊断总体方向**正确**（whoosh 路线 + 频段下移 + 峰值压低 + 改下扫），但有**一处技术判断需要修正**：

| 主理人诊断 | 结论 | 说明 |
| --- | --- | --- |
| 「用户要的一直是 whoosh 路线」 | ✅ **确认，且证据比预期更强** | 见 §0：audio-bible 原本就规定 whoosh，是代码跑偏。用户从未听到过正确版本 |
| 「扫到 4200Hz 太高」 | ✅ **确认，并可以说得更准** | 不只是「高」。关键在于：`_noise` 是**衰减型包络**，声音**最后残留的部分**停在 `sweepTo` 上。原版把余音停在 4200 Hz —— 等响曲线上人耳最敏感的位置（耳道共振 3–4 kHz）→ **最持久的部分刚好最刺耳**。详见 §2.3 |
| 「q=0.7 **带宽偏窄**导致沙沙发毛 / 接近哨声」 | ❌ **判断反了，须修正** | Q=0.7 在 2 极点带通上是 **1.92 个八度**的带宽，属于**很宽**，不是窄。而且：**哨声来自高 Q（≥4），不是低 Q** —— 两个症状的成因方向相反。「沙沙发毛」的真凶是**宽带 + 中心频率高**（能量摊在 1.5k–8k）。详见 §2.4 |
| 「带宽放宽（更像气声而非沙声）」 | ❌ **按此执行会更糟** | 在 2 极点带通上再放宽 Q，只会让更多 4–8 kHz 嘶声漏过来，**沙感加重**。**气声 vs 沙声由「中心频率」决定，不由「带宽」决定。** 正确动作是：**中心频率大幅下移 + Q 适度调高**（0.7 → 1.3）以陡化裙边、挡住 3–5 kHz。详见 §2.4 |
| 「峰值压得更低」 | ✅ **确认，且本规格压得比建议更狠** | 见 §2.6：等效响度比 v2.0 低约 **14 dB**（≈ 感知响度只剩 1/2.6） |
| 「下扫比上扫更放松、更不抢戏」 | ✅ **确认，且有三条独立理由支撑**（不止「放松」） | 见 §2.3：物理多普勒、**包络一致性**、刺耳区规避。其中「包络一致性」是本原语特有的硬理由 |
| 「是否需要双层叠加才有运动感」（授权我判断） | ❌ **不需要，坚决单层** | 运动感来自**扫频**，不来自层数。加第二层只会同时增加音量、复杂度与「打击感」，三样都与用户的四个关键词冲突。详见 §2.8 |

> **一句话修正**：主理人的药方里「频段下移 + 下扫 + 压低峰值」三味是对的，**「带宽放宽」这一味要换成「带宽适度收紧」**。

## 2. 轻柔气流 whoosh 合成参数表（Soft Whoosh Synthesis Spec）

### 2.1 主参数表（★ 单层，就一行代码）

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 使用原语 | **`_noise`**（单层） | 不用 `_tone`，不加第二层（论证见 §2.8） |
| 声源 | 白噪声 BufferSource | `_noise` 每次调用重新生成随机 buffer |
| 滤波器类型 | **`bandpass`**（`_noise` 默认，不传 `type`） | 见 §2.4 |
| 带通中心起点 `band` | **1800 Hz** | |
| 带通中心终点 `sweepTo` | **450 Hz** | ⚠️ 这是「扫频速率控制」而非「你会听到的终点」，见 §2.3 |
| `q` | **1.3** | ≈ 1.08 个八度带宽，气声而非沙声 |
| `dur` | **0.11 s** | `_noise` 的 `dur` 才是真实时长（§2.5） |
| `peak` | **0.038** | 标准档，三档见 §2.7 |
| attack | **0.006 s**（原语硬编码，不可配） | **不需要改**，论证见 §2.5 |
| 随机微抖 | **不加** | 噪声本身已随机，论证见 §2.9 |
| 输出总线 | `sfxGain`（0.8），默认 dest | 不改总线 |

**一行落地形态：**

```js
this._noise({ dur: 0.11, peak: 0.038, band: 1800, q: 1.3, sweepTo: 450 });
```

> 这就是全部。用户要「简单」，规格也真的做到了字面意义上的简单 —— **一次原语调用、零辅助变量、零随机数、零第二层**。

### 2.2 设计原理（为什么这样调）

物体从耳边掠过的物理过程，逐条映射到参数：

| 物理特征 | 听感词 | 合成对应 |
| --- | --- | --- |
| 气流扰动是宽带无音高的 | 「气声」「不是叮当」 | 白噪声源，非振荡器 |
| 物体靠近→掠过→远离，频谱质心下移（多普勒 + 高频先衰减） | **「运动感」「嗖」** | 带通中心 **1800 → 450 Hz 下扫** |
| 远离时高频损失最快（空气吸收 ∝ f²） | 「越来越柔」「远去」 | 下扫 + 指数衰减包络天然耦合 |
| 掠过是一瞬间的事，不是持续风声 | 「不拖沓」 | 可听时长 ≈ 58 ms（§2.3） |
| 轻质物体（纸/布）而非重物 | **「轻柔」** | 峰值 0.038、中心频段避开 3–4 kHz 刺耳区 |
| 它只是背景里发生的一件小事 | **「不干扰」** | 等效响度比 `buttonTap` 低约 15 dB（§2.6） |

### 2.3 ⚠️ 扫频：为什么写 1800→450，但你只会听到 1670→870

**这是本规格最反直觉、也最容易被误改的一点，工程与后续调音者必须理解。**

`_noise` 的包络与扫频**共用同一个 `dur`**：

```js
g.gain.linearRampToValueAtTime(peak, now + 0.006);          // 6ms 冲到峰值
g.gain.exponentialRampToValueAtTime(0.0001, now + dur);     // 指数衰减到 -80dB
filt.frequency.exponentialRampToValueAtTime(sweepTo, now + dur);  // 同一时刻到达 sweepTo
```

增益要在 `dur` 内从 `peak` 指数衰减到 0.0001（衰减 **74 dB**），意味着**声音在 `dur` 走完之前很久就已经听不见了**。核算（`dur=0.11, peak=0.038`）：

| 时刻 | 归一化 τ=t/dur | 增益（相对峰值） | 此刻带通中心 |
| --- | --- | --- | --- |
| 6 ms | 0.055 | **0 dB（峰值）** | **1669 Hz** |
| 30 ms | 0.273 | −13.3 dB | 1256 Hz |
| **58 ms** | **0.526** | **−25 dB（可听下沿）** | **868 Hz** |
| 89 ms | 0.809 | −40 dB（几乎无声） | 586 Hz |
| 110 ms | 1.0 | −74 dB（`src.stop`） | 450 Hz |

**→ 实际可听的扫程是 1669 → 868 Hz，约 0.94 个八度，历时约 58 ms。**

三条由此产生的重要推论：

1. **`sweepTo: 450` 是「扫频速率旋钮」，不是「终点音高」。** 想让运动感更强，改 `sweepTo` 更低（扫得更快）；不要指望真的听到 450 Hz。
2. **可听扫程与 `dur` 无关。** 包络和扫频都以 `dur` 为参数，等比缩放 —— 改 `dur` 只改快慢，**不改扫过多少个八度**。扫程只由 `sweepTo/band` 的比值决定。
3. **可听落点 1669→868 Hz 正好落在 audio-bible 规定的 800 Hz–1.5 kHz 区间内。** 参数写 1800/450 看起来超纲，实际听感完全合规 —— §0 那条「圣经是对的」在数值上也成立。

**对照原版为什么运动感反而不足：** 原版 `band:2200 → sweepTo:4200, dur:0.09`，比值 1.909，可听扫程 = 2265 → 3120 Hz，**只有 0.46 个八度，且全程在 3–4 kHz 刺耳区**。

> **所以原版的病根是「移动太少 + 太亮」，v3.0 的处方是「移动加倍 + 整体下移一个八度」——
> 更多运动、更少亮度。这一句就是 v3.0 的全部设计意图。**

**为什么必须下扫（三条独立理由，任何一条都足以定案）：**

| # | 理由 | 说明 |
| --- | --- | --- |
| 1 | **物理正确** | 物体掠过后远离，多普勒 + 空气高频吸收都让频谱质心下移。上扫 = 物体朝你加速冲来 = 紧张/警示语义，与「不干扰」直接冲突 |
| 2 | **包络一致性（本原语特有的硬理由）** | `_noise` 是**衰减型**包络。自然界没有任何东西「越来越轻的同时越来越高」—— 除了正在消失的哨声。原版「衰减 + 上扫」是自相矛盾的组合，这正是它听起来**发毛、不自然**的核心原因，比「太亮」更根本 |
| 3 | **刺耳区规避** | 衰减包络让声音**最后残留的部分**停在 `sweepTo`。下扫把余音停在 500–900 Hz（人耳不敏感）；上扫把余音停在 4200 Hz（等响曲线最敏感点）→ **最持久的部分刚好最刺耳** |

### 2.4 Q 值：为什么是 1.3（而不是主理人建议的「放宽」）

**先纠正一个概念**：`q` 越小 → 带宽越**宽**。2 极点带通的 −3 dB 带宽（八度）= `2·asinh(1/2Q)/ln2`：

| Q | 带宽（八度） | 中心 1669 Hz 时 4 kHz 处的衰减 | 听感 | 判定 |
| --- | --- | --- | --- | --- |
| 0.7（原版） | **1.92 八度** | **−4.7 dB** | 能量摊到 1.5k–8k，全是嘶声 | ❌ **这才是「沙沙发毛」的真凶** |
| 1.0（圣经建议） | 1.39 八度 | −7.0 dB | 可用 | 🔸 可接受 |
| **1.3（本规格）** | **1.08 八度** | **−8.9 dB** | 气声、有明确「一股」的形态 | ✅ **采用** |
| 2.0 | 0.72 八度 | −12.1 dB | 开始有共振音高感 | 🔸 偏窄 |
| ≥ 4 | ≤ 0.36 八度 | — | 滤波器振铃 → **哨音** | ❌ 这才是「哨声」的成因 |

**关键澄清：「沙声」与「哨声」的成因方向相反，不能用同一个动作解决。**

- **沙声（嘶/毛）** = 宽带 + 中心频率高 → 解法是**降中心频率**（主力）+ **适度提 Q**（辅助，陡化裙边）
- **哨声（尖锐音高）** = 高 Q（≥4）→ 本规格 Q=1.3，离得很远，**不存在哨音风险**

主理人建议的「带宽放宽」若照做（Q 0.7 → 0.5），2 极点带通的裙边会更平缓，**4–8 kHz 漏得更多，沙感加重**。所以本规格反向操作：**中心频率下移一个八度（主力手段）+ Q 从 0.7 提到 1.3（辅助手段）**。

> **气声 vs 沙声由「中心频率」决定，不由「带宽」决定。** Q=1.3 保留了 1.08 个八度的宽度，足够「气」；真正把沙感干掉的是 1669→868 Hz 这个位置。

**为什么不用 `lowpass`？**（`_noise` 支持 `opts.type`，零成本可切）
2 极点 `lowpass` 的高频滚降是 12 dB/oct，比 `bandpass` 上裙边的 6 dB/oct **更能压住沙感**（4 kHz 处约 −14 dB，比 bandpass 好 5 dB）。但 `lowpass` 会**完整保留 450 Hz 以下的低频噪声**，听感从「嗖」变成「呼」（更闷、更重），与「轻柔」的**轻**字冲突，且这部分能量在手机外放上完全浪费。
→ **默认 `bandpass`**。但作为**已验证的备选**记录在 §3.2：若实测仍嫌沙，加一个 `type: 'lowpass'` 即可，无需其他改动。

### 2.5 两头平滑：结论是**不需要改原语**（逐条论证）

需求特别关注「起止不能有咔哒（click）」。已逐行核对 `_noise`（`audio.js:181-215`），**结论：本规格不会产生 click，原语无需任何改动。**

**收尾（结束端）—— 完全安全：**

```js
g.gain.exponentialRampToValueAtTime(0.0001, now + dur);   // 终点 -80 dB
src.stop(now + dur);                                       // 此刻才切断
```

`src.stop` 发生时增益已是 0.0001（−80 dB），截断一个 −80 dB 的信号在数学上是不连续，在听感上完全不存在。✅

**起振（开始端）—— 也安全，但理由需要说清：**

```js
g.gain.setValueAtTime(0.0001, now);
g.gain.linearRampToValueAtTime(peak, now + 0.006);   // 6ms 线性上升
```

| 关注点 | 分析 | 结论 |
| --- | --- | --- |
| 有没有电平跳变？ | 起点 0.0001（−80 dB），**值本身连续**，只有一阶导数在 t=0 与 t=6ms 处不连续 | ✅ 无跳变型 click |
| 导数不连续会不会有 splatter？ | 斜坡拐点的频谱能量按 −12 dB/oct 滚降，且集中在 1/6ms ≈ 167 Hz 以下；本音效峰值仅 −30 dBFS 量级 | ✅ 远低于可闻阈 |
| 增益节点在滤波器之后（`src→filt→g`），滤波器帮不上忙 | 属实，但由上两行可知本来就不需要滤波器兜底 | ✅ 无影响 |
| 6 ms 会不会太陡、不够「轻柔」？ | 6 ms 不是 click（click 阈值约 < 1–2 ms），但确实是**打击型起振**而非**渐强型起振** | ⚠️ 见下方专门讨论 |

**关于 6 ms 硬编码 attack：这是特性，不是限制。**

理想的「风声型」whoosh 会用 20–40 ms 的渐强做出「由远及近」的膨胀感。`_noise` 做不到（attack 硬编码）。**但对本场景而言，做不到反而是对的：**

> `swipe` 是**输入反馈音**，它的首要职责是与手指划动的瞬间**对齐**。
> 若改成 30 ms 渐强，声音的感知起点（能量达到可辨阈的时刻）会推迟约 20–25 ms，玩家会觉得**音效比手感慢半拍、发糊、粘滞**。
> 交互音效的黄金准则是「**起振要准、收尾要柔**」—— `_noise` 的「6 ms 起 + 指数收」正好是这个形状。

**→ 明确结论：不改原语。** 若将来真要做「渐强型」whoosh（例如广告进场 `adStart` 的 whoosh in），最小改动方案如下，**但本次不采纳、不要落地**：

```js
// 【v3.0 不采纳，仅备案】_noise 支持可配 attack 的最小改动（向后兼容，默认仍是 6ms）
const atk = opts.attack != null ? Math.min(opts.attack, dur * 0.5) : 0.006;
g.gain.linearRampToValueAtTime(peak, now + atk);
```

（`Math.min(..., dur*0.5)` 是必需的护栏，防止 `attack > dur` 时两个 ramp 时间点逆序 —— 参见 §2.10 纪律 3。）

### 2.6 增益预算：它到底有多轻（相对其他事件的实测位置）

**⚠️ 先说一个关键概念，否则数字会被误读：`peak` 参数在噪声与振荡器之间不可直接比较。**

`_noise` 的 `peak` 是施加在**带通白噪声**上的包络峰值。白噪声经 Q=1.3 带通后，功率只剩全带的约 9%；再算上噪声本身波峰因数，**同样的 `peak` 数值，噪声的等效响度远低于正弦/三角波**。核算（RMS，`peak=0.038`）：

- 均匀白噪声 RMS = 0.577
- Q=1.3 带通等效噪声带宽 ≈ π·1669/(2·1.3) ≈ 2017 Hz，占奈奎斯特带宽 22050 Hz 的 9.1% → 幅度系数 0.302
- **v3.0 swipe RMS ≈ 0.577 × 0.302 × 0.038 = 0.00663**

| 事件 | 合成 | RMS（过 sfxGain 前） | v3.0 swipe 相对它 |
| --- | --- | --- | --- |
| `win` | 5× triangle @0.20 | 0.1155 | **−24.8 dB** |
| `newBest` | triangle @0.18 | 0.1039 | **−23.9 dB** |
| `buttonTap` | triangle 700Hz @0.12 | 0.0693 | **−20.4 dB** |
| `invalidMove` | sine 320Hz @0.08 | 0.0566 | **−18.6 dB** |
| **v2.0 木质嗒**（被否版） | tri 0.10 + noise 0.055 | 0.0584 | **−18.9 dB** |
| **原版 whoosh**（被否版） | noise 0.05 / Q0.7 / 宽带 | 0.01512 | **−7.2 dB**（再叠加频率加权约 −15 dB） |
| **v3.0 swipe（本规格）** | noise 0.038 / Q1.3 | **0.00663** | — |

**修正为感知响度**（噪声跨约 5 个 Bark 临界带，有 +4~6 dB 响度叠加；中心 ~1.2 kHz 与 1 kHz 敏感度相当）：

| 对比对象 | **等效感知响度差** | 直观含义 |
| --- | --- | --- |
| vs `win` / `newBest` | **约 −20 dB** | 庆祝音完全压得住它，绝不抢戏 ✅ |
| vs `buttonTap` | **约 −15 dB** | 比按一次按钮明显轻，符合「高频事件应更轻」✅ |
| vs **v2.0 木质嗒** | **约 −14 dB** | **感知响度只剩原来的 1/2.6** ✅ 这是「不干扰」的量化交付 |

**过 `sfxGain`(0.8) 后的绝对位置**：RMS ≈ 0.0053，瞬时峰值约 0.021 → **约 −33 dBFS**，距离削波极远；末端 `DynamicsCompressor` 根本不会被触发。

> **关于 `peak` 数值本身**：0.038 相对前版噪声层 0.055 是 **−3.2 dB**，相对前版两层理论和 0.155 是 **−12.2 dB**。
> 但如上所述，**真实响度差（−14 dB）远大于数字看起来的差**，因为 v3.0 去掉了 300 Hz triangle 那个响度主力，且带通更窄。**用户会感觉安静了非常多。**

### 2.7 三档增益（供用户试听后拍板）

单层方案的好处：**调音量就是改一个数，音色完全不变。**

| 档位 | `peak` | 相对标准档 | 相对 v2.0 感知响度 | 适用 |
| --- | --- | --- | --- | --- |
| **轻**（几乎隐形） | **0.026** | −3.3 dB | ≈ −17 dB | 觉得还是能注意到它、想让它彻底退到背景 |
| **标准（推荐交付值）** | **0.038** | 0 dB | ≈ −14 dB | 默认 |
| **亮**（存在感明确） | **0.052** | +2.7 dB | ≈ −11 dB | 觉得听不见、反馈不明确（**优先调这里，不要动 `band`**） |

> **重要**：即便是「亮」档（0.052），等效响度仍比 v2.0 木质嗒低约 **11 dB**、比 `buttonTap` 低约 **12 dB** —— **三档全都在「不抢戏」的安全区内**，用户可以放心试听，不存在选错档位就变吵的风险。
>
> **调音顺序纪律**：听不清 → 先升档到 0.052；仍不清 → 再考虑 `band` 1800→2100（会变亮，慎用）。**永远不要为了「听得见」而去提高 `band`** —— 那是走回原版老路。

### 2.8 为什么坚持单层（不加第二层）

用户明确说了「简单」。我的专业判断也支持单层，理由如下：

| 若加第二层 | 后果 | 判定 |
| --- | --- | --- |
| 加低频 `_tone`（如 v2.0 的 300 Hz triangle） | 立刻带回**「打击/落点」语义** —— 这正是方案 C 被否的根因。物体掠过不该有「咚」 | ❌ 语义冲突 |
| 加高频噪声层增强「s」感 | 把能量送回 3–4 kHz 刺耳区 | ❌ 直接违反「轻柔」 |
| 加第二层同款噪声做厚度 | 响度 +3 dB，且噪声叠噪声只会更「糊」，不会更「有形」 | ❌ 违反「不干扰」 |

**核心论证：运动感的唯一来源是扫频（§2.3 已给出 0.94 个八度的可听扫程），与层数无关。** 方案 A（三层 sine、零扫频）恰好是反证 —— **层数最多的那版，运动感为零。**

→ **单层已经足够，且是唯一同时满足「简单 + 轻柔 + 不干扰」的解。**

### 2.9 随机微抖：不加（并给出理由）

**判定：不需要任何 `Math.random()`。**

`_noise` 在 `audio.js:195` 每次调用都会**重新生成一整段全新的随机白噪声 buffer**：

```js
for (let i = 0; i < frames; i++) data[i] = Math.random() * 2 - 1;
```

→ **每一次滑动听到的都是物理上不同的噪声波形**，天然不可能机械重复。这与音高型音效（sine/triangle）完全不同 —— 那些才需要人为抖 `freq`。

额外抖动反而有害：

| 抖动对象 | 后果 |
| --- | --- |
| 抖 `band` | 每次「气流的粗细/材质」在变，听成音效不稳定，反而更引人注意（违反「不干扰」） |
| 抖 `peak` | 忽大忽小，比恒定音量更容易被察觉 |
| 抖 `dur` | 改变扫频速率 → 每次「物体速度」不同，混乱 |

→ **不加抖动。既是专业判断，也正好满足用户的「简单」。**

### 2.10 ⚠️ `_noise` 参数语义（工程必读，沿用 v2.0 §2.5 并更新）

| | `_tone`（`audio.js:152-177`） | `_noise`（`audio.js:181-215`） |
| --- | --- | --- |
| 实际发声长度 | `attack + release` | **`dur`**（buffer 长度 + `src.stop` + 包络终点三者同步） |
| `dur` 是否影响时长 | ❌ 不影响（显式传 `release` 时仅作占位） | ✅ **直接决定时长** |
| attack | ✅ 可配 `opts.attack` | ❌ **硬编码 6 ms**（`audio.js:205`） |
| release | ✅ 可配 | ❌ 不可配（固定为指数衰减到 `dur`） |
| `when` / 调度偏移 | ✅ 支持 | ❌ **不支持**（内部固定 `this._now()`，`audio.js:185`） |
| `type` | 波形（sine/triangle/…） | **滤波器类型**（bandpass/lowpass/…），语义不同 |
| `dest` | ✅ 支持 | ✅ 支持 |

**三条落地纪律：**

1. **只传 `_noise` 认识的键**：`dur` / `peak` / `band` / `q` / `type` / `sweepTo` / `dest`。传 `attack` / `release` / `when` 会被**静默忽略**（不报错、不生效），是最容易踩的坑。
2. **v3.0 不需要 `when`，也不需要 `const base = this._now()`** —— 单层单次调用，没有对齐问题。**不要保留 v2.0 遗留的 `base` / `f0` 变量**（会变成未使用变量）。
3. **`dur` 必须 > 0.006**，否则包络两个 ramp 时间点逆序。本规格 `dur = 0.11`，余量充足。

### 2.11 连滑不糊：叠加核算

玩家快速连滑时会短时间多次触发，需确认不会形成「噪音墙」。

| 项 | 数值 |
| --- | --- |
| 单次可听时长（至 −25 dB） | **≈ 58 ms** |
| 单次完整窗口（至 `src.stop`） | 110 ms |
| 人类连续滑动的最小舒适间隔 | 约 **120–150 ms** |
| 正常连滑时的重叠 | **基本为零**（58 ms < 120 ms） |
| 极端连发（长按键盘 repeat，间隔 ~50 ms）时的重叠层数 | 最多 2 层可听 |

**关键：噪声之间是非相干叠加，按功率相加，不是按幅度相加。**

| 同时可听层数 | 电平增量 | 等效 `peak` |
| --- | --- | --- |
| 1 | 0 dB | 0.038 |
| 2 | **+3.0 dB** | 0.054 |
| 3 | +4.8 dB | 0.066 |
| 4 | +6.0 dB | 0.076 |

→ 即便极端情况 4 层齐发（现实中不可能），等效响度仍低于 v2.0 木质嗒**单次**的水平。**不会形成噪音墙。** ✅

> **因此 v2.0 §3.3 的「重触发保护」（45 ms 闸门）在 v3.0 中已无必要，明确不实现** —— 少一个状态变量（`this._lastSwipeAt`）、少一处 constructor 改动，符合「简单」。

### 2.12 复音预算与性能（audio-bible §3.2：SFX ≤ 12 voice）

| 项 | 值 |
| --- | --- |
| 单次 swipe 节点开销 | 1 × BufferSource + 1 × BiquadFilter + 1 × Gain |
| 声源数（voice） | **1**（v1.0 玻璃叮 3、v2.0 木质嗒 2 → **本方案最省**） |
| Oscillator 数 | **0** |
| 达到 12 voice 需要 | 110 ms 内连发 12 次有效移动（≈109 次/秒），不可能 |
| buffer 开销 | 110 ms @44.1kHz ≈ 4851 个 float ≈ **19 KB**，用完即弃由 GC 回收；填充循环约 4851 次迭代，微秒级 |
| 结论 | **无需对象池或实例上限** |

> 相比 v2.0 唯一的性能回退：noise buffer 从 28 ms（4.8 KB）增至 110 ms（19 KB）。绝对值极小，且每次滑动才分配一次，对帧率无可测影响。

### 2.13 手机外放适配（相比 v2.0 是明显改善）

v2.0 的 300 Hz 体振层在手机外放上会被大幅衰减（外放普遍在 400 Hz 以下严重滚降）—— 这是 v2.0 的固有短板。

**v3.0 的可听频段 1669 → 868 Hz 恰好落在手机外放响应最好的区间（约 800 Hz–5 kHz）**，因此：

- ✅ 手机外放上听感与耳机**高度一致**，不会像 v2.0 那样「在手机上只剩一声嚓」；
- ✅ 无低频依赖 → 不存在「缺失基频」补偿问题；
- ⚠️ 反过来需注意：手机外放在 1–2 kHz 往往有**峰值染色**，可能让它听起来比耳机上**略明显一点**。若手机上觉得偏吵，走 §2.7「轻」档（0.026）。

1. **只改一处**：`src/audio.js` 的 `case 'swipe'`（**235–248 行**整块），用 §3.1 的代码块整段替换。**一行合成代码**：


2. **删干净**：旧的 `const base` / `const f0` / `this._tone({...triangle 300Hz...})` 全部删除。swipe 从此**不产生任何 Oscillator**。
